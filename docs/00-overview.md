# FACP 架构总览

## 1. 问题定义

### 1.1 现状
Claude Desktop、Qoder（国内版 / 国际版）、WorkBuddy（国内版 / 国际版）、豆包（国内版 / 国际版）、Codex Desktop 等桌面 AI 客户端各自为政：

- 会话互不相通，跨 App 协作靠人肉复制粘贴
- 各自有独立账号体系、独立后端、独立风控池
- 国内版与国际版是完全隔离的两套产品，能力、合规边界、网络要求都不同
- 每个客户端只会"对话"，**没有操控其他程序的手脚**

### 1.2 人的成本
一个工程师在多个 AI 之间协调，实际在做的是：打开软件、找到对应会话、把上下文搬过去、转述需求、把结果搬回来、再打开另一个软件……这正是最该被自动化掉的部分。

### 1.3 目标
让这些**闭源、不可改造**的桌面客户端，成为联邦网络里的对等节点：

1. 互相发现（谁在线、擅长什么、属于哪个域）
2. 互相唤醒（按需拉起未启动的进程）
3. 互相定位会话（准确切换到已加入协作区的那个对话）
4. 互相传递上下文（带结构化信封，而不是整段原文倾倒）
5. 互相派工（Agent 自主判断该找谁）
6. 具备执行手脚（替代人手操作窗口、输入、点击、文件、程序）

## 2. 为什么不用中心调度器

| | 中心调度（Supervisor） | 对等 Mesh（本方案） |
|---|---|---|
| 决策位置 | 外部调度程序 | **每个 Agent 本体** |
| 能力认知 | 调度器需要维护全量能力表 | 各节点自注册，按需查询 |
| 单点故障 | 调度器挂了全停 | 单节点故障可隔离 |
| 扩展新 Agent | 改调度逻辑 | 新增一个 Sidecar 即可 |
| 符合真实协作 | 像流水线派单 | 像工程师之间互相喊话 |

> **关键限定**：去掉调度器 ≠ 放开自由聊天。跨节点通信必须是**结构化服务调用**，自由文本只能封装在 `payload` 内部。

## 3. 三层职责分离（最重要的架构约束）

```
┌──────────────────────────────────────────────────────────────┐
│ L1  FACP 协作平面（基础设施，不做任何业务决策）                 │
│   Registry      节点注册 / 心跳 / 能力查询                     │
│   Message Bus   NATS，异步投递结构化信令                       │
│   FSHub         联邦会话（FSID）元数据 / 域策略 / 审计          │
│   Observer      观测 + 人工开关（不是调度器）                   │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只传信令与工件引用
┌───────────────────────────┴──────────────────────────────────┐
│ L2  适配层                                                    │
│   Sidecar-*     一 App 一边车：进程 / 窗口 / 会话 / 注入 / 嗅探 │
│   Executor      通用桌面动作执行节点（可被任意节点调用）        │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────┴──────────────────────────────────┐
│ L3  原生桌面 Agent（不可改造，保持原样）                       │
│   Claude Desktop / Qoder / WorkBuddy / 豆包 / Codex …          │
└──────────────────────────────────────────────────────────────┘
```

| 层 | 只做什么 | 绝不做 |
|---|---|---|
| L1 协作平面 | 注册、投递、域校验、审计、观测 | 任务规划、决定下一步谁干活 |
| L2 Sidecar | 单一 App 的生命周期、会话映射、消息注入与嗅探 | 操作别的 App、通用桌面点击 |
| L2 Executor | 按传入的 steps 串行执行原子动作 | 自主规划、主动发起协作调用 |
| L3 Agent | 推理、判断、产出协作请求、消费回执 | 直接操作其他软件 |

## 4. 核心设计原则

1. **能力自治**：Agent 自己判断要不要求助，协作平面不干预业务意图。
2. **安全域默认拒绝**：CN / INTL 默认不通，跨域是会话级特权（见 FACP-001）。
3. **身份不可混淆**：同软件不同版本、同版本不同账号，都是不同节点。
4. **契约优先**：跨节点只有结构化信封，禁止自由文本广播。
5. **关注点分离**：信令 / 适配 / 执行 / 推理四件事，各自独立可替换。
6. **故障域隔离**：单 App 崩溃、单 Sidecar 异常不拖垮全网。
7. **用户可介入**：任何会话可暂停、可拒绝单条请求、可剥夺跨域、可急停 Executor。
8. **增量适配**：优先 App 官方本地 API（Tier1），UI 自动化仅兜底（Tier3）。

## 5. 关键概念速查

| 概念 | 定义 | 详见 |
|---|---|---|
| Node | 一个 Sidecar 或 Executor 实例，独立身份、独立安全域 | FACP-001 |
| FSID | 联邦会话 ID，跨 App 的协作项目根标识 | FACP-002 §4 |
| COLLAB_CALL / REPLY | 唯一允许的两类跨节点消息 | FACP-002 §5 |
| security_domain | `cn` / `intl`，默认通信边界 | FACP-001 §3 |
| call_depth | 调用嵌套层数，硬上限防死循环 | FACP-002 §6 |
| inject / sniff | Sidecar 向 App 注入任务 / 从 App 嗅探协作指令 | FACP-003 §4 |
| steps | Executor 的原子动作数组，串行执行 | FACP-004 §3 |

## 6. 一次完整协作的时序（三节点）

```
用户 ──> Claude Desktop（intl）
              │ 判断：Triton 审查超出能力边界
              │ 输出 ```fcp COLLAB_CALL(intent=code_review)
              ▼
        Sidecar-Claude ── DomainGuard ──> NATS node.qoder-intl-01
                                              ▼
                                    Sidecar-Qoder-intl
                                      ├ 进程未启动 → start
                                      ├ 查 fsid 本地会话 → 无则建并绑定
                                      ├ 激活窗口 / 切换到该会话
                                      └ inject(payload)
                                              ▼
                                        Qoder 自主审查
                                              │ 输出 REPLY
                                              ▼
                                    Sidecar 回投 reply_subject
                                              ▼
        Sidecar-Claude 注入回原会话 ──> Claude 继续推理
                                              │ 需要落盘改代码
                                              │ COLLAB_CALL(intent=desktop_execute)
                                              ▼
                                    Executor(facp-executor-01)
                                      ├ 高危动作前置校验
                                      ├ steps 串行执行 + 逐步截图
                                      └ 返回 step_results
```

> 全过程：**没有任何外部程序决定"下一步找谁"**，每一次转向都由当时那个 Agent 自己发起。

## 7. 边界与非目标

**明确不做：**

- ❌ 统一所有 AI 到一个聊天窗口（保留各 App 原生 UI 与历史）
- ❌ 替换各 Agent 内部推理与工具调用逻辑
- ❌ 破解客户端加密会话、绕过登录
- ❌ 接管各 App 的账号、订阅、付费
- ❌ 在协作平面里做模型路由 / 负载调度（这属于 Agent 本体的判断）
- ❌ 无限制跨域传输敏感资料

**当前技术风险（见 FACP-007）：**

- UI 自动化注入易被客户端反自动化识别 → 优先 Tier1
- 闭源 App 无本地 API 时，读会话上下文能力受限
- Executor 是最高风险组件，默认锁死高危动作
